=========================
Main Simulation Workflow
=========================

This document provides a highly detailed walkthrough of the primary workflows within the ``mcstas_gisans`` framework. It covers the complete journey of a neutron from the McStas simulation output, through the BornAgain sample interaction, and finally to the data processing, plotting, and automated fitting stages. 

The framework is designed to bridge the gap between Monte Carlo ray-tracing (McStas) and Distorted Wave Born Approximation (DWBA) calculations (BornAgain) while maintaining rigorous coordinate system mappings to experimental NeXus data.

1. The Simulation Step (``mg_run``)
-----------------------------------

The primary simulation script is executed via the ``mg_run`` command line utility. This step bridges the McStas instrument model and the BornAgain sample model.

Loading Neutrons
~~~~~~~~~~~~~~~~
The simulation begins by loading a neutron event file (MCPL format) generated by a McStas ``MCPL_output`` component at the sample position. 

- **TOF Filtering:** If the experiment utilizes Time-of-Flight (TOF) data, the script uses the associated TOF monitor data from the McStas simulation to filter out invalid neutron events based on minimum and maximum TOF/wavelength cuts.
- **Coordinate Transformations:** The positions and velocity vectors of the loaded neutrons are strictly transformed into the standard **BornAgain coordinate system** (where the z-axis is normal to the sample surface). This ensures that the DWBA physics engine processes the scattering correctly.

Sample Interaction
~~~~~~~~~~~~~~~~~~
The ``mg_run`` script dynamically imports a sample model, either a built-in one from the ``bornagain_samples/`` directory or a local Python file (specified by the ``--model`` argument; see :doc:`custom_sample`).
For every incoming neutron event, BornAgain calculates the scattering probabilities (intensities) for a wide range of outgoing directions, sampled at ``-n``/``--outgoing_directions`` points (or independently in the horizontal/vertical directions with ``--outgoing_directions_horizontal``/``--outgoing_directions_vertical``).

BornAgain itself can internally multithread each of these per-neutron DWBA calculations. This is controlled with ``--bornagain_number_of_threads`` (default: let BornAgain choose), independently of ``-p``/``--parallel_processes``, which controls how many *neutrons* are processed concurrently by separate worker processes. When running many parallel processes yourself (e.g. on a shared cluster node), set ``--bornagain_number_of_threads 1`` to avoid oversubscribing CPU cores.

Detector Propagation
~~~~~~~~~~~~~~~~~~~~
The outgoing scattered rays are propagated mathematically from the BornAgain sample origin to the detector surface. 
Crucially, during this step, the scattered vectors are **transformed back into the experimental NeXus coordinate system**. The detector geometry (distance, pixel size, number of pixels) is read from the specified ``--instrument`` configuration.

Output Data
~~~~~~~~~~~
Unlike older versions of the codebase which calculated Q-space variables and saved to raw Numpy ``.npz`` arrays, the modern workflow strictly exports the data into a **Scipp HDF5 dataset (.h5)**. 
- For non-TOF simulations, this is a 2D spatial grid (y and z pixel bins) representing the intensity on the detector.
- For TOF simulations, this is a multi-dimensional event dataset preserving TOF/wavelength axes, allowing for highly flexible post-processing.

2. Beam Alignment (``beam_centre_correction``)
----------------------------------------------

Before comparing simulated scattering with experimental NeXus measurements, it is critical to ensure that both datasets are physically aligned on the detector grid. Small instrument misalignments in real-world measurements can cause the direct beam to hit off-center pixels.

The ``mg_beam_centre_correction`` utility is used to align the instrument based on an **Experimental Direct Beam NeXus File**. 

- The script mathematically shifts the experimental direct beam on the detector grid using SciPy optimization (`scipy.optimize.root`) until its exact center-of-mass is located perfectly at :math:`(Q_y, Q_z) = (0, 0)`.
- It outputs the precise rigid-body spatial offset (`[x, y]` in meters) required to achieve this alignment.
- This computed offset must then be applied to subsequent sample simulations to ensure perfect overlap. It is applied by passing the offset flag (e.g. ``--instrument_detector_centre_offset X Y`` to ``mg_run``, or ``--nxs_instrument_detector_centre_offset X Y`` to ``mg_plot``).

Important Coordinate Units & Orientations
-----------------------------------------

**Physical Units:**
- **Q-space:** All momentum transfer values (:math:`Q_y`, :math:`Q_z`) and plot cut ranges (e.g., ``--q_min``, ``--q_max``, ``--y_plot_range``, ``--z_plot_range``) are expressed in :math:`\text{nm}^{-1}`. 
- **Wavelength:** Particle wavelengths are always given in **Angstroms** (:math:`\text{\AA}`).
- **Spatial:** Detector sizes and center offsets are in **meters**.

**Sample Orientations:**
The framework relies on the ``--sample_orientation`` flag to map the BornAgain scattering output onto the detector frame. The codes are:
- **0:** Vertical sample, beam hitting from the left (-90 degree rotation).
- **1:** Horizontal sample, normal pointing up (+Y NeXus axis). This is the default.
- **2:** Vertical sample, beam hitting from the right (+90 degree rotation).

**Wavelength Inputs (TOF vs. Monochromatic):**
- For **TOF instruments** (e.g., SAGA, LOKI, SKADI), you must pass ``--wavelength`` (used for MCPL TOF filtering and T0 calculation). Passing ``--wavelength_selected`` will raise a parser error.
- For **Monochromatic/non-TOF instruments** (e.g., D22), you must pass ``--wavelength_selected`` (used to strictly define the monochromatic wavelength). Passing ``--wavelength`` will raise a parser error.

3. Data Processing and Plotting (``mg_plot``)
---------------------------------------------

The ``mg_plot`` script takes the simulated ``.h5`` files and performs the Q-space transformations and visualizations.

NeXus Integration
~~~~~~~~~~~~~~~~~
If an experimental NeXus file is provided (``--nxs``), the generic ``nexus_reader.py`` module is invoked. This module uses the physical ``Instrument`` object parameters to convert both the simulated spatial hits and the experimental detector pixels into rigorous Q-space coordinates ($Q_y$, $Q_z$). *(Note: Plotted figures follow the convention where the y-axis is horizontal and the z-axis is vertical).*

``mg_plot --nxs`` accepts multiple files; each one is plotted as its own labelled dataset (paired positionally with ``--nxs_label``, if given). This is different from ``mg_fit --nxs``, described below, where multiple files are instead summed together into a single dataset to fit against.

Upscaling to Experiment Time
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Because Monte Carlo simulations output normalized rates (e.g., neutrons per second), the ``mg_plot`` script provides the ``--experiment_time`` argument.
- The normalized simulated intensities are multiplied by the requested experiment time.
- To realistically simulate detector counting noise, random integer sampling from a **Poisson distribution** is applied to each pixel bin, matching the statistical variance of the real measurement. In ``mg_plot`` this always happens whenever ``--experiment_time`` is given (there is no option to disable it there); in ``mg_fit``, by contrast, it is *off* by default and only enabled with ``--poisson_sampling``, precisely so the objective function stays smooth for the optimizer (see the fitting section below).
- A flat background (``--background``) can also be added for visualization parity.

Visualizations
~~~~~~~~~~~~~~
The script can generate:
- 2D detector heatmaps (Qy vs Qz) side-by-side or overlaid.
- 1D sliced projections across specified Q-ranges for highly precise intensity comparisons.

4. Parameter Scans and Automated Fitting (``mg_fit``)
------------------------------------------------------

Instead of manually guessing sample parameters (like particle radius, lattice spacing, or defect abundance) and re-running ``mg_run`` and ``mg_plot`` by hand, users can invoke the ``mg_fit`` workflow. It builds directly on top of ``mg_run`` (it shares and extends the same CLI options — instrument, sample model, MCPL filtering, masking, etc.) and adds experimental comparison, masking, scanning and optimization on top. Exactly one of ``--scan``, ``--fit``, ``--fit2`` or ``--fit_common`` must be given (unless only ``--mask_view`` is requested, see below).

Experimental data (``--nxs``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``--nxs`` accepts one or more NeXus files. If multiple files are given (e.g. a measurement split into several segments), their raw detector counts are summed together before being compared against the simulation; in that case ``--experiment_time`` should be set to the *cumulative* experiment time across all given files, not the time of a single segment. All files must produce detector histograms of the same shape, or ``mg_fit`` raises an error.

Masking (``--mask_*``)
~~~~~~~~~~~~~~~~~~~~~~
Before comparing simulation to measurement, regions of the detector can be excluded from (or forced into) the loss calculation — typically to remove the specular peak and direct beam, which otherwise dominate the fit. See the masking options in :doc:`cli_reference` (``--mask_qy_min_cut``/``--mask_qy_max_cut``/``--mask_qz_min_cut``/``--mask_qz_max_cut`` for simple cuts, ``--mask_exclude_q_box``/``--mask_include_q_box`` for rectangular Q-regions, each repeatable). Exclusions are always applied before inclusions. Pass ``--mask_view`` to render the raw vs. masked NeXus data and exit immediately, without running any simulation — a fast way to check a masking configuration before committing to a full scan or fit.

Mode 1: Parameter scan (``--scan``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``--scan name v1 v2 ...`` runs one simulation per listed value (or the Cartesian product of values, when repeated for several parameters), without any optimization — useful for building intuition about a parameter's effect, or for a brute-force grid search. Results (loss metric per configuration, and optionally comparison plots via ``--png``) are written to ``--output_dir`` (default ``scan_results``).

Mode 2: Automated fitting (``--fit``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- The script takes a parameterized sample model and the (summed) experimental NeXus data.
- It uses SciPy optimizers selected with ``--optimizer``: **Nelder-Mead** (default) or **Powell** for local/derivative-free search, or **Differential Evolution** for global exploration (which requires finite bounds on every fitted parameter).
- During each iteration, a full BornAgain simulation is executed, and a loss metric — ``reduced_chi2`` (default) or ``log_residual``, selected with ``--loss_function`` — is calculated over the unmasked detector region.
- The optimizer stops once its convergence tolerances (``--xatol``, ``--fatol``) are met or the evaluation budget (``--max_evals``) is exhausted; it does not necessarily reach a perfect match. Use ``--fit_integer`` to constrain specific parameters (e.g. a discrete layer count) to integer values during optimization, and ``--gif`` to render an animation of the fit's progress.
- Poisson noise sampling (``--poisson_sampling``) is off by default during scans and fits, since random per-evaluation noise would make the objective function non-smooth and hinder convergence.

**Usage Example:**
To run an automated fit, you must specify your starting parameters, step bounds, and experimental data.

.. code-block:: bash

   mg_fit mcstas_output.mcpl.gz --nxs d22_experiment.nxs --instrument d22 \
     --model my_custom_sample --wavelength_selected 6.0 \
     --fit radius 50 100 \
     --fit height 20 50 \
     --mask_exclude_q_box -0.05 0.05 -0.02 0.02

Segmented measurement example (multiple ``--nxs`` files, summed, with the matching cumulative experiment time):

.. code-block:: bash

   mg_fit mcstas_output.mcpl.gz --nxs d22_run1.nxs d22_run2.nxs d22_run3.nxs \
     --experiment_time 10800 --instrument d22 \
     --model my_custom_sample --wavelength_selected 6.0 \
     --fit radius 50 100

**Custom Sample Models:**
The ``--model`` argument dynamically imports either a built-in Python script from the ``bornagain_samples/`` directory, or a local file (absolute path, or relative to your current working directory). To create a custom parameterized sample for fitting, add a Python file containing a ``get_sample(**kwargs)`` function that builds and returns a ``ba.MultiLayer``. The framework automatically parses the ``--fit``/``--scan``/``--sample_arguments`` CLI flags and passes the corresponding values as kwargs into your function (any kwarg not accepted by your ``get_sample`` signature — unless it declares ``**kwargs`` — is ignored with a warning).

Joint / dual-sample fitting
~~~~~~~~~~~~~~~~~~~~~~~~~~~
``mg_fit`` can also fit two related samples simultaneously against two (possibly different) experimental datasets, sharing some parameters between them while letting others vary independently — e.g. fitting a common particle ``radius`` across two measurements taken at different sample orientations or conditions, while letting an interference/lattice parameter differ between them. Use ``--fit_common`` for parameters shared by both samples, ``--fit2`` for parameters specific to the secondary sample, and ``--nxs2`` for the secondary NeXus dataset (other ``*2`` options like ``--filename2``, ``--alpha2``, ``--sample_arguments2``, ``--intensity_factor2``, ``--experiment_time2`` and ``--background2`` override the corresponding primary option for sample 2 only, defaulting to the primary value when omitted). See :doc:`cli_reference` for the full flag list.
